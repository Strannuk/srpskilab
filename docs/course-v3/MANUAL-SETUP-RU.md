# SrpskiLab 3.0 — что необходимо выполнить вручную

**Дата:** 29.09.2026  
**Назначение:** безопасная приёмка редакторского проекта и последующая публикация после лингвистической экспертизы.  
**Внимание:** Пакет в текущем состоянии — **не релиз всей версии 3.0**. Полные отдельные черновые уроки: `m1l1`–`m4l5` (20 штук). Для остальных 245 есть индивидуальные рабочие планы, но не проверенное новое содержание. Боевое приложение 2.1 и база данных не изменены.

## 0. Не удаляйте работающий сайт

Нельзя запускать исходную схему `202609290001_schema.sql` или сид `202609290002_seed.sql` второй раз в существующей базе как способ «обновить контент». Сид устроен как `ON CONFLICT DO UPDATE` и **может перезаписать версии содержания**, которые были позднее повышены. Никогда не выключайте RLS ради устранения ошибки. Не вставляйте `service_role` в `.env.local` либо `VITE_*`.

## 1. Что сделать в Visual Studio Code

1. Сохраните текущую папку проекта и экспортируйте данные аккаунтов/прогресса согласно правилам вашей базы. В существующем Git-репозитории выполните:

   ```powershell
   git status
   git switch -c feature/course-v3-editorial
   ```

   Если ветка с таким именем уже существует, используйте другое имя. Ветка НЕ должна быть производственной для Cloudflare.

2. Распакуйте архив рабочего проекта в отдельную папку; сравните и скопируйте изменения только после просмотра diff. НЕ перезаписывайте собственный `.env.local`; этот файл не входит в архив. Если применяете в существующей Git-папке, сначала сохраните локальные незакоммиченные файлы.
3. Запустите:

   ```powershell
   npm ci
   npm run typecheck
   npm run content:verify
   npm run content:v3:validate
   # Если установлен FFmpeg, валидатор дополнительно проверит декодирование MP3 через ffprobe.
   npm run test
   npm run build
   npm run dev
   ```

   Сообщайте о любом красном сообщении. Из-за ограничения Linux-окружения тестовая **production-сборка Vite ещё требует подтверждения на Windows**.

4. Откройте **только локальные** адреса:

   - http://localhost:5173/editorial/curriculum — 265 **учебных каркасов**, можно фильтровать, читать цели и слушать отдельные старые фрагменты.
   - http://localhost:5173/pilot/m1l1 ... http://localhost:5173/pilot/m4l5 — двадцать учебных черновиков A0. В локальном режиме результаты не сохраняются в облако и не разблокируют уроки.

5. После проверки файлов отправьте **только редакторскую ветку** на GitHub:

   ```powershell
   git status
   git add .
   git commit -m "feat: v3 editorial workshop and A0 module drafts"
   git push -u origin feature/course-v3-editorial
   ```

   Убедитесь, что нет `.env.local`, `.env`, приватных SQL с ответами, тестовых JSON с личными данными и `node_modules`. **Не сливайте ветку в `main` до готовности релиза.**

## 2. Нужно ли уже сейчас менять Supabase?

**Нет.** Пилотные занятия работают локально, не вызывают Supabase, не обновляют таблицы и не выдают зачёты. Менять `course_lessons`, `lesson_question_bank` и `lesson_progress` сейчас нельзя — веб-интерфейс основного сайта всё ещё отправляет старые ID вопросов. При несовпадении семи ID сервер отвергает попытку (`invalid question set`), а обновление `content_version` без согласованной смены вопросов делает исторические попытки трудноразличимыми.

## 3. Прочитайте состояние существующей БД в Supabase SQL Editor

Это **только SELECT**, безопасный для просмотра. В своём Supabase-проекте откройте **SQL Editor** и выполните:

```sql
select count(*) as lessons_count from public.course_lessons;
select count(*) as words_count from public.word_registry;
select count(*) as private_lesson_questions from private.lesson_question_bank;
select count(*) as private_exam_questions from private.exam_question_bank;
```

Если применены именно исходные сведения, ожидается **265 уроков, 714 слов** и при полностью заполненном закрытом банке **1855 вопросов (7 × 265) плюс 100 экзаменационных**. Число 265/714 само по себе не означает, что закрытые ответы заполнены! Базовый `202609290002_seed.sql` из этого архива загружает **только публичный реестр уроков и слова**, но **не заполняет приватный банк ответов**.

Дополнительные безопасные проверки:

```sql
select id, position, level, content_version, published
from public.course_lessons
where id in ('m1l1','m1l2','m1l3','m1l4','m1l5')
order by position;

select lesson_id, count(*) as question_count
from private.lesson_question_bank
group by lesson_id
having count(*) <> 7
order by lesson_id;

select level, count(*) as question_count
from private.exam_question_bank
group by level
order by level;

select count(*) as attempts_count from public.lesson_attempts;
select count(*) as progress_count from public.lesson_progress;
```

Если закрытый банк пуст, **сначала нужно восстановить исходный банк версии 2.1**. В отдельном защищённом файле поставки `SrpskiLab-legacy-answer-bank-PRIVATE.sql` находится воспроизведённый по исходным `legacy/site/curriculum*.js` банк, у которого **каждый из 1855 + 100 идентификаторов, текстов вопросов и наборов вариантов сравнен со всеми опубликованными вопросами текущего `catalog.json`**. Это не ответы, угаданные по случайной формулировке: программа `scripts/prepare-private-bank.cjs` делает строгую проверку идентичности. Однако методическая корректность старых вопросов этим не подтверждается.

**Как применять ТОЛЬКО если оба банка в БД пустые и все 265 уроков имеют `content_version = 1`:**

1. Сделайте полную резервную копию текущей БД и проверьте, что у вас выбран именно проект SrpskiLab. Если пользовательские данные уже есть, особенно внимательно обеспечьте восстановление без потери новых попыток.
2. Откройте **отдельный приватный SQL-файл**, не вставляйте его в GitHub и не копируйте в `src/`, `public/`, `.env*` или Cloudflare.
3. В Supabase SQL Editor вставьте SQL из файла и запустите вручную. В начале SQL предусмотрена транзакция и жёсткие проверки: команда прервётся без изменения, если банк не пуст, число уроков отличается от 265 или курс уже не исходной версии 1.
4. Повторите проверки в разделе 3. Ожидается `1855` вопросов для уроков и `100` для экзаменов; затем проверьте тестовую отправку **первого старого урока v2.1** в браузере.
5. Если какой-либо банк уже частично заполнен, **не запускайте SQL**: он специально откажется от выполнения. Нужно отдельно исследовать несовпадения, а не замещать ответы вслепую.

**Важно:** восстановление старого банка не активирует новые уроки v3. Новые черновики намеренно не подключены к зачётам. Генератор для исходной версии можно запустить локально отдельно: `node scripts/prepare-private-bank.cjs`; он создаёт файл в исключённой из Git папке `supabase/private/`. Не публикуйте его, даже если сам репозиторий приватный.

## 4. Как обновлять Supabase только ПОСЛЕ утверждения материала v3

1. Сначала завершите контент и редакторское/аудио QA всех уроков, которые вы публикуете. На тестовом Supabase-проекте или отдельной staging-базе создайте резервную копию `public.course_lessons`, `private.lesson_question_bank`, `private.exam_question_bank`, пользовательских `lesson_progress` и `lesson_attempts` (а также auth/users в полноценном DB backup). Нужна точка восстановления всей БД, а не только CSV с одной таблицей. Доступность Point-in-Time Recovery зависит от текущего тарифа.
2. Для **каждого обновляемого урока** должны согласованно совпадать: его старый стабильный `id`, новая версия контента, ровно семь публичных `question_id`, ровно семь строк в `private.lesson_question_bank`, порядок и допустимые ответы. Серверная и клиентская версии должны развертываться согласованно, чтобы старые запросы не ломались во время публикации. Лучше создать новую отдельную версию банка ответов и обеспечить временную совместимость старой/новой версий, чем удалять текущие семь вопросов до развёртывания клиента.
3. Создайте новую **версионированную SQL-миграцию**, НЕ редактируйте выполненные исторические файлы `202609290001_schema.sql`/`202609290002_seed.sql`. SQL сначала проверяет ожидаемые версии и количество строк, затем в транзакции добавляет/активирует банк ответов, переключает метаданные `course_lessons.content_version`, проверяет constraints и фиксирует изменения. Для совместимого развертывания потребуется при необходимости изменить SQL RPC так, чтобы учитывался `content_version` от клиента (только со строгой проверкой на сервере).
4. **Не переписывайте `lesson_progress`, `lesson_attempts` и историю экзаменов.** Сохраняйте `completed`, `best_score`, `attempt_key`, старую `content_version` в истории попыток. Новые достижения проверяются отдельно. Обновлять `course_lessons.content_version` без обновления серверной функции и клиентских ID нельзя.
5. Прогоните на тестовом Supabase минимум два разных пользователя: пользователь A не видит B; 69%/70% на уроках; 79%/80% на экзаменах; следующий урок закрыт на сервере до нужного зачёта; старый пройденный урок не теряет отметку; повторный запрос не создаёт вторую попытку; другой пользователь видит собственный прогресс после повторного входа.
6. Только после этого переносите миграцию на рабочий Supabase, под согласованное окно обслуживания, и публикуйте синхронно клиентскую сборку. Проверьте прямой URL каждого обновлённого урока и сценарий отката. Никогда не копируйте секретный `service_role` в клиентские файлы и не коммитьте полный список правильных ответов в публичный репозиторий.

**Примечание для текущего пакета:** SQL-миграции с заменой ответов v3 пока нет — потому что для неё отсутствуют подтверждённая редактором полная программа, реальная приёмка аудио и новый совместимый production-контракт. Запускать миграцию раньше было бы ошибкой.

## 5. Что понадобится на Cloudflare Workers

После готовности релиза и проверки ветки:

1. GitHub: смержить в `main` только утверждённые изменения.
2. В Cloudflare Worker `srpskilab` проверить настройки **Build variables and secrets**: `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` должны содержать реальные публичные значения от вашего Supabase-проекта. НЕ `service_role`.
3. Команда сборки `npm run build`, команда публикации `npx wrangler deploy`. Облачная сборка использует `wrangler.jsonc` и `assets.directory: ./dist`.
4. Убедиться, что **публичные страницы** отображают только `published` контент. Маршруты `/pilot/*` и `/editorial/curriculum` в этом проекте включены строго для `import.meta.env.DEV` и не должны быть доступны в опубликованной сборке. После публикации дополнительно проверить, что не опубликованы приватные аудио, черновики и ключи.
5. Проверить `https://srpskilab.belokamensky-kirill.workers.dev` в обычном и приватном браузере, настройки Auth URL Configuration и допустимые Redirect URLs в Supabase. Точный URL в вашем аккаунте может измениться.
6. Проверьте SMTP, восстановление пароля, удаление аккаунта (Supabase Edge Function `delete-account` нужно разворачивать отдельно), заголовки безопасности, аудио на Android/iOS и резервные копии.

## 6. Восстановление и откат

- Если новая сборка не работает — верните предыдущую удачную публикацию Cloudflare и не меняйте серверные вопросы до восстановления согласованного API.
- Если новая миграция DB ошибочна, выполняйте rollback только из заранее проверенного снимка/обратной миграции с учётом **новых пользовательских попыток**, появившихся после миграции. Простая перезапись всей БД старым дампом может потерять новые данные.
- Если вопрос выведен из использования, сохраните историю старого `content_version` и метаданные; не удаляйте историю зачётов ради упрощения.

## 7. Проверки, которые невозможно честно завершить автоматически

- Носитель/компетентный преподаватель должен проверить сербскую лексику, грамматику, естественность диалогов, ударение, фонетику и латиницу/кириллицу.
- Не менее нескольких учащихся должны пройти пробный материал без подсказок; отдельно оцениваются письмо и говорение.
- Проверить права на использование старого и нового синтезированного звука до публичной публикации. Локальные редакторские MP3 специально исключены из Git и `dist`.
- Реальные данные Cloudflare/Supabase не доступны через загруженный архив: результат настоящих запросов в production остаётся за владельцем/подключёнными инструментами.
